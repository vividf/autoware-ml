# Dataset Pipeline

> **What this covers:** how raw datasets become GPU-ready batches — the `DataModule` /
> `Dataset` base classes, the `databases/` caching layer, collation, and the boundary to
> model-owned GPU preprocessing.
>
> Prerequisite: [../architecture/data_flow.md](../architecture/data_flow.md) (the 7-hop
> overview). This is the deep version. Augmentation gets its own doc:
> [augmentation.md](augmentation.md).

---

## 1. Why the pipeline is split the way it is

A perception dataset is big (LiDAR sweeps, multi-camera images) and every model wants the
data slightly differently. The framework separates four concerns so each can change
independently:

| Concern | Owner | Runs where |
| ------- | ----- | ---------- |
| *Which samples exist + their metadata* | `Dataset.get_data_info` | CPU, on demand |
| *Load files + augment* | `TransformsCompose` (per-sample) | CPU, in dataloader workers |
| *Merge samples into a batch* | `DataModule.collate_fn` (`collation_map`) | CPU, worker |
| *GPU per-batch shaping* (voxelize, normalize) | `DataPreprocessing` (model-owned) | GPU, per batch |

The golden rule (repeated from the overview because it causes the most confusion):
**`get_data_info` returns metadata, not tensors.** Files are loaded in transforms. This keeps
datasets trivial and makes loading configurable per experiment.

## 2. `Dataset` — the metadata source (`datamodule/base.py:76`)

```python
class Dataset(TorchDataset, ABC):
    def __init__(self, dataset_transforms: TransformsCompose | None = None, **kwargs):
        self.dataset_transforms = dataset_transforms

    def __getitem__(self, index):                                   # :93
        input_dict = self.get_data_info(index)                      # ← metadata dict
        context = PipelineContext(dataset=self, index=index)        # ← orchestration state
        return self.apply_transforms(input_dict, self.dataset_transforms, context)

    @abstractmethod
    def get_data_info(self, index) -> dict[str, Any]: ...           # :106  YOU implement
```

### A real `get_data_info` (`datamodule/nuscenes/detection3d.py:108`)

```python
def get_data_info(self, index):
    sample = self.data_infos[index]
    lidar_path = self._resolve_lidar_path(sample)
    return {
        "instances":   sample.get("instances", []),   # raw annotation records (NOT gt_boxes yet)
        "class_names": self.class_names,
        "name_mapping": self.name_mapping,
        "label_to_category": self.label_to_category,
        "sample_token": sample["token"],
        "timestamp":   sample.get("timestamp"),
        "lidar_path":  lidar_path,                     # a PATH — points are loaded by a transform
        "num_pts_feats": int(...),                     # feature width used to reshape the file
        "sweeps":      self._resolve_sweeps(sample),   # historical frame metadata
    }
```

Notice: `instances` are *raw* records (a later transform, `LoadAnnotations3D`, turns them
into `gt_boxes`/`gt_labels`), and `lidar_path` is a *path* (`LoadPointsFromMultiSweeps`
reads it). The dataset's `__init__` did the only file I/O: `pickle.load(ann_file)` once
(`nuscenes/detection3d.py:65`).

### `PipelineContext` (`datamodule/pipeline_context.py`)

Passed to every transform. Carries `dataset`, `index`, and an RNG, and exposes
`sample_secondary(pre_transform)` so a *mixing* augmentation (copy-paste, FrustumMix) can pull
a second, differently-indexed sample without polluting the sample dict. Keeping orchestration
state out of the data dict is a deliberate information-hiding choice.

## 3. `DataModule` — dataloaders + collation (`datamodule/base.py:139`)

```python
class DataModule(L.LightningDataModule, ABC):
    def __init__(self,
                 collation_map=None,
                 train_transforms=None, val_transforms=None, test_transforms=None, predict_transforms=None,
                 train_dataloader_cfg=None, val_dataloader_cfg=None, test_dataloader_cfg=None, predict_dataloader_cfg=None):
        ...
        self.collation_map = dict(collation_map or {})
        if "offset" in self.collation_map:                           # :200
            raise ValueError("'offset' is a reserved collation key generated by concat inputs.")

    @abstractmethod
    def _create_dataset(self, split, dataset_transforms=None) -> Dataset: ...   # :249  YOU implement
```

### What a subclass implements

Almost nothing — just `_create_dataset`. From NuScenes (`nuscenes/detection3d.py:181`):

```python
def _create_dataset(self, split, dataset_transforms=None):
    return NuscenesDetection3DDataset(
        data_root=self.data_root,
        ann_file=self.ann_files[split],      # {"train":..., "val":..., "test":..., "predict":...}
        class_names=self.class_names,
        name_mapping=self.name_mapping,
        dataset_transforms=dataset_transforms,   # ← the split's transform pipeline, injected here
    )
```

### `setup()` maps a Lightning stage to splits (`base.py:268`)

```python
stage_splits = {"fit": ["train", "val"], "validate": ["val"], "test": ["test"], "predict": ["predict"]}
splits = ["train","val","test","predict"] if stage is None else stage_splits[stage]
for split in splits:
    transforms = getattr(self, f"{split}_transforms")   # the per-split TransformsCompose
    setattr(self, f"{split}_dataset", self._create_dataset(split, transforms))
```

So `trainer.fit(...)` triggers `setup("fit")` → builds `train_dataset` (with
`train_transforms`) and `val_dataset` (with `val_transforms`).

### Dataloaders (`base.py:298`)

```python
def _create_dataloader(self, split):
    dataset = getattr(self, f"{split}_dataset")
    cfg = getattr(self, f"{split}_dataloader_cfg")       # a DataLoaderConfig
    return DataLoader(dataset=dataset, collate_fn=self.collate_fn, **cfg.to_dataloader_kwargs())
```

`DataLoaderConfig` (`base.py:40`) is a dataclass: `batch_size`, `num_workers`, `pin_memory`,
`persistent_workers`, `shuffle`, `drop_last`. `_coerce_dataloader_cfg` accepts a dataclass,
a plain dict, or a Hydra `DictConfig` and normalizes it — this is the "Hydra boundary" where
YAML mappings become typed objects. Note `persistent_workers` is auto-forced off when
`num_workers == 0` (`base.py:71`).

> Some datamodules override `_create_dataloader` — e.g. T4 detection adds repeat-factor frame
> sampling (`DistributedWeightedRandomSampler`) to rebalance rare classes for the **train**
> split only. NuScenes detection does not.

## 4. Collation — the batching engine (`base.py:423`)

`collation_map` is the contract that turns a list of per-sample dicts into one batch dict.
It is a **strict whitelist**: only listed keys survive.

```python
def collate_fn(self, batch):
    result, primary_lengths, deferred_index_concat = {}, None, []
    for key, strategy in self.collation_map.items():
        missing = [i for i, s in enumerate(batch) if key not in s]
        if missing:
            logger.warning("Key '%s' declared but missing from samples %s. Skipping...", key, missing)
            continue                                            # :456  predict/deploy tolerate this
        values = [self._coerce_value(s[key]) for s in batch]    # numpy → tensor
        match strategy:
            case CollationStrategy.STACK:  result[key] = self._apply_stack(key, values)      # shapes must match
            case CollationStrategy.CONCAT:
                tensor, lengths = self._apply_concat(values)
                result[key] = tensor
                if primary_lengths is None:                     # first concat key = primary space
                    primary_lengths = lengths
                    result["offset"] = torch.cumsum(lengths, dim=0)   # :475
            case CollationStrategy.INDEX_CONCAT: deferred_index_concat.append((key, values))  # done after
            case CollationStrategy.LIST:   result[key] = list(values)
    ...
```

| Strategy | Use it for | Produces |
| -------- | ---------- | -------- |
| `stack` | fixed-shape tensors (images) | `(B, ...)` tensor; mismatched shapes raise `ValueError` |
| `concat` | variable-length point clouds (PTv3) | one long tensor + `batch["offset"]` (cumulative lengths) |
| `index_concat` | per-point indices into the concatenated cloud | indices shifted to stay valid after concat (needs a `concat` key) |
| `list` | ragged per-sample data (CenterPoint points/boxes) | a Python list, untouched |

CenterPoint's map (from its `base.yaml`):

```yaml
collation_map: { points: list, gt_boxes: list, gt_labels: list }
```

It uses `list` because point counts differ per sample and voxelization is deferred to the GPU
preprocessing step. A point-based model like PTv3 instead uses `concat`/`index_concat` and
relies on `batch["offset"]` to recover per-sample boundaries.

**`_coerce_value` nuance (`base.py:327`):** numpy arrays become contiguous tensors; **numpy
scalars keep their dtype** — this is why float64 epoch-second timestamps survive collation
without being quantized to ~256-second steps by float32. Non-numeric objects pass through
(so `list` can carry arbitrary Python objects).

**`offset` is reserved** — declaring it in `collation_map` raises at construction (`base.py:200`).

## 5. Two data stacks coexist

This surprises people reading the code, so it's worth stating plainly. There are **two
independent data stacks**:

| | Primary stack (dict-based) | Multi-task / database stack (typed) |
| --- | --- | --- |
| Base classes | `datamodule/base.py` `Dataset`/`DataModule` | `datamodule/multi_task/` + `databases/` |
| Sample type | plain `dict` | Pydantic dataclasses (`MultiTaskGTSample`) |
| Info source | pickled `.pkl` info files | Parquet cache of `DatasetRecord`s |
| Collation | `DataModule.collate_fn` + `collation_map` | `MultiTaskGTBatch.collate_gt_samples` (padding) |
| Used by | CenterPoint, most detection/segmentation on NuScenes & T4 | multi-task / newer T4 flows |

Most models you'll meet (CenterPoint, BEVFusion, StreamPETR, FRNet, PTv3) use the **primary
stack** with `.pkl` info files. The database stack is the newer, typed path.

## 6. The `databases/` layer — offline dataset → validated cache

`databases/` is an **offline preprocessing/caching layer**, separate from the datamodule. Its
job: parse a raw T4/NuScenes dataset (via `t4-devkit`) once, validate it against **Pydantic
schemas**, and write a columnar **Parquet cache** of `DatasetRecord`s.

```text
raw T4 dataset (JSON tables)
   → T4RecordsGenerator (reads via t4-devkit, per sample)
   → T4SampleRecord.to_dataset_record()
   → DatasetRecord  (frozen, strict Pydantic model)
   → Polars DataFrame → Parquet (cached under a hash of the config)
```

Key files (`docs/databases/t4dataset.md` documents this fully):

| Path | Role |
| ---- | ---- |
| `databases/base_database.py` | `BaseDatabase`: version/paths, `database_hash` (cache invalidation), load helpers |
| `databases/t4dataset/t4dataset.py` | `T4Dataset(BaseDatabase)`: parallel record generation across scenarios |
| `databases/t4dataset/t4records_generator.py` | reads T4 annotations, extracts lidar frames/sweeps/boxes |
| `databases/schemas/dataset_schemas.py` | `DatasetRecord`, `DatasetTableSchema` (frozen Pydantic) |
| `databases/box3d_pipelines/` | box label remapping / merging / velocity clipping at cache-build time |

The **cache is keyed by a hash of the config + schema** (`database_hash`), so changing class
names, label maps, or the schema invalidates it automatically — reproducibility by
construction.

## 7. Building info files: `autoware-ml create-dataset`

```bash
autoware-ml create-dataset --dataset nuscenes --task detection3d \
    --root-path data/nuscenes --out-dir data/nuscenes/info --version v1.0-trainval
```

Dispatch: `cli.py` `create-dataset` → `autoware_ml.scripts.create_dataset:main` →
`autoware_ml.tools.dataset.runner.generate_dataset(...)`. This produces the `.pkl` info files
that the primary-stack datasets load (e.g. `nuscenes_infos_train.pkl`).

> Note: there is also a `configs/generators/` + `scripts/generate_dataset.py` path that
> exercises the **database** stack. It is a separate, non-CLI-wired demo (its docstring says
> it will be removed); don't confuse it with `create-dataset`.

## 8. Handoff to the model (GPU preprocessing)

After collation, Lightning moves the batch to the GPU and calls the model's
`on_after_batch_transfer`, which runs the model-owned `DataPreprocessing`
(`preprocessing/base.py`):

```python
class DataPreprocessing:
    def __call__(self, batch):
        for layer in self.pipeline:
            batch |= layer(batch)          # dict-in/dict-out, on device
        return batch
```

For CenterPoint the single layer is `PointPillarPreprocessor`
(`preprocessing/detection3d/point_pillar.py`), which voxelizes each sample's `points` and
**adds** `voxels`, `num_points`, `voxel_coords`:

```python
for batch_index, points in enumerate(points_list):
    voxels, coords, num_points = hard_voxelize(points, voxel_size, point_cloud_range,
                                               self.max_num_points, self.max_voxels)
    batch_column = torch.full((coords.shape[0], 1), batch_index, ...)   # prepend batch idx
    coords = torch.cat([batch_column, coords], dim=1)                   # → [batch, z, y, x]
    ...
outputs["voxels"], outputs["num_points"], outputs["voxel_coords"] = ...
```

Why here and not in a CPU transform: voxelization is heavy, GPU-friendly, and *model-specific*
(the grid must match the model). This split keeps per-sample CPU augmentation independent from
per-batch GPU shaping. More in [../model/model_architecture.md](../model/model_architecture.md).

## End-to-end example (NuScenes CenterPoint)

```text
NuscenesDetection3DDataset.__init__      pickle.load(nuscenes_infos_train.pkl)  → self.data_infos
  │
__getitem__(i)
  ├─ get_data_info(i)                     {instances, lidar_path, sweeps, class_names, ...}
  └─ apply_transforms(...)                train_transforms pipeline:
        LoadAnnotations3D                 instances → gt_boxes(N,9), gt_labels, gt_num_points
        LoadPointsFromMultiSweeps         lidar_path + sweeps → points (with time-lag col)
        RandomFlip3D / GlobalRotScaleTrans   augment points + boxes jointly
        PointsRangeFilter / ObjectRangeFilter   crop
        PointShuffle
  ▼ sample dict {points, gt_boxes, gt_labels, ...}
collate_fn (collation_map: points/gt_boxes/gt_labels = list)
  ▼ batch {points:[...], gt_boxes:[...], gt_labels:[...]}
── GPU ──
on_after_batch_transfer → PointPillarPreprocessor  → adds voxels, num_points, voxel_coords
  ▼ model.forward(voxels, num_points, voxel_coords)
```

## Common debugging cases

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| `KeyError` for a key in `forward`/`compute_metrics` | not in `collation_map` (dropped) | add it to `collation_map` |
| Warning "declared but missing from samples" | a transform didn't produce it, or it's a train-only key during predict | expected for predict/deploy; else check the transform |
| `stack` `ValueError: sample k has shape …` | variable-size tensor collated with `stack` | switch that key to `list` or `concat` |
| `index_concat requires a concat key` | used `index_concat` alone | add a `concat` key to define the primary space |
| Timestamps look quantized/rounded | numeric precision lost | rely on `_coerce_value` preserving numpy scalar dtype; keep float64 |
| `FileNotFoundError` on lidar path | `data_root` / `AUTOWARE_ML_DATA_PATH` wrong, or info paths relative | check `set_data_path.sh` and `datamodule.data_root` |
| Info file `.pkl` not found | didn't run `create-dataset`, or `--out-dir` mismatch | regenerate; check `train_ann_file` interpolation |
| Cache seems stale (database stack) | it isn't — `database_hash` invalidates on config/schema change | delete/rebuild only if you changed raw data |

## Common modification scenarios

| I want to… | Do this |
| ---------- | ------- |
| Add a new dataset | Subclass `Dataset` (implement `get_data_info`) + `DataModule` (implement `_create_dataset`); write a task config. See `docs/contributing/adding-models.md` |
| Add a key the model needs | Produce it in a transform/preprocessing **and** add it to `collation_map` **and** add a matching `forward` param |
| Rebalance rare classes | Use / configure repeat-factor `train_frame_sampling` (T4 detection) |
| Change batch size / workers per split | `datamodule.<split>_dataloader_cfg` in the config |
| Use a different point-batching scheme | Change strategies in `collation_map` (`list` ↔ `concat`/`index_concat`) and adapt the model |
| Keep metadata for debugging | add e.g. `sample_token: list` to `collation_map` |
